### F1 — Silent stall: `resolve_gh_repo` blocks indefinitely on network (Priority 2)

**File:** `quorum/src/main.rs:168-190`

`resolve_gh_repo` spawns `gh repo view --json nameWithOwner` as a synchronous subprocess
with no timeout. This is called during `quorum serve` startup (main.rs:829, 847) to
resolve `--self-repo` and `merge_executor.gh_repo`. If GitHub's API is unresponsive or
the `gh` binary hangs (auth prompt, network partition, DNS stall), the `quorum serve`
process blocks indefinitely before it even opens the database — no heartbeat, no journal
row, no daemon_lock entry. A supervisor watching for exit 75 will never fire.

**Failure scenario:** Operator launches `scripts/serve-supervisor.sh` on a machine with a
misconfigured `gh` auth or during a GitHub outage. The supervisor's child process hangs at
the `gh repo view` call. No daemon_lock is held, so a second supervisor launch would
start a second daemon (violating the single-daemon invariant) — except it too hangs at
the same point. The system is silently stalled with no recovery path except manual kill.

**Proposed fix-task:**

```
Wrap the `resolve_gh_repo` and `resolve_gh_repo` calls in a timeout.
Use `std::process::Command` with a child.wait_timeout() pattern, or
spawn with a watchdog thread that kills the child after 15 seconds.
On timeout, fall back to `None` (the same fallback as a failed `gh`
invocation). Emit a warning to stderr so the operator sees the timeout.
```

### F2 — Stale schema comment: `depends_on` gates on `done`, not `closed` (Priority 3)

**File:** `quorum-core/src/schema.sql:65`

The schema.sql comment reads:

> Claim auto-pick + explicit --task-id both gate on every listed dep being status='closed'
> (reviewed + finalized).

But `closed` is not a valid task status (the status enum is: open, working, in-review,
rework, merging, done, failed, cancelled). The actual SQL in `tasks.rs:246` and
`tasks.rs:369` checks `d.status = 'done'`. This was flagged in the baseline audit's
stale-vocabulary sweep (cockpit.rs references `closed` too).

**Failure scenario:** No runtime bug — the comment does not execute. But a future
developer reading schema.sql who trusts the comment may write code checking
`status='closed'` (which matches zero rows), silently breaking dependency gating. The
comment has already survived multiple schema versions uncorrected.

**Proposed fix-task:**

```
Replace 'closed' with 'done' in the depends_on comment in schema.sql
line 65. Also update any other in-code comment that references 'closed'
as a task status (grep for "closed" in .rs and .sql files — the baseline
audit identified cockpit.rs:389,578 as having the same issue).
```

### F3 — Test gap: no v19→v20 migration test (Priority 4)

**File:** `quorum-core/src/db.rs:312-333` (the v20 migration) and `db.rs` test module

The v20 migration adds four columns to `tasks` (author, reviewer, rework_round,
review_only). The migration chain has dedicated tests for v1→v2, v2→v3, v3→v4, v4→v5,
v5→v6, v7→v8, v8→v9, v9→v10, v12→v13, v13→v14, v14→v15, v16→v17, v17→v18. No test
covers v19→v20 explicitly.

The v17→v18 test implicitly exercises v19 and v20 (it starts at v17, opens with the
current binary, and asserts `user_version == SCHEMA_VERSION`), but it does not assert
the v20 columns exist or have correct defaults. A regression in the v20 migration
(e.g., a typo in the column name or a wrong default) would not be caught by any
existing test if the ALTER fails silently.

**Failure scenario:** A DB at exactly v19 (daemon_lock present, lifecycle columns absent)
is opened by the current binary. The v20 migration silently fails (e.g., due to a
column_exists check bug or a conditional guard error like the v9/v10 collision caught by
Gravel-m38). Tasks would be created without author/reviewer/rework_round fields,
breaking the lifecycle state machine.

**Proposed fix-task:**

```
Add `migrates_v19_to_v20_adds_lifecycle_columns` test to db.rs::tests.
Hand-craft a v19 DB with the v19 shape (daemon_lock present,
tasks without author/reviewer/rework_round/review_only, user_version=19).
Insert a seed task row. Open via `open()`, assert user_version == SCHEMA_VERSION,
assert all four columns exist, and assert the seed row's defaults
(author=NULL, reviewer=NULL, rework_round=0, review_only=0).
```

### F4 — Test gap: no concurrent branch allocation test (Priority 4)

**File:** `quorum-core/src/branches.rs:67-141`

`allocate_for_task` uses the correct double-check pattern (read-then-lock-then-recheck),
and the UNIQUE collision retry is bounded. However, there is no multi-process or
multi-thread test exercising concurrent branch allocations for the same or different
tasks. The claim-race canary (`race.rs`) covers the task-claim path but not the branch
allocation that happens immediately after a successful claim (main.rs:297-309).

The branch allocation happens outside the claim transaction (the claim commits at
`tasks::claim`, then `branches::allocate_for_task` opens a new transaction). Two
concurrent CLI processes that both win claims on different tasks in the same instant
could race on the `allocate_for_task` UNIQUE(branch) collision retry.

**Failure scenario:** Two CLI processes claim different tasks with identical slugified
titles + agent suffixes. Both pass the pre-txn lookup (no existing row), both enter
BEGIN IMMEDIATE. One commits first; the other hits UNIQUE(branch) and retries with
suffix `-1`. This is correct behavior — but if three or more collide, the 4th collision
exhausts the retry budget and returns a raw SQLITE_CONSTRAINT_UNIQUE error (exit 3)
instead of a descriptive message. The test gap means this path is unverified.

**Proposed fix-task:**

```
Add a concurrent branch-allocation test to branches.rs or as an
integration test: N threads (or processes) each calling
allocate_for_task for different task_ids but with identical slugs.
Assert: each gets a distinct branch, no errors. Also add a unit test
that exhausts the 3-retry budget and asserts the error is surfaced
cleanly (currently returns raw SQLITE_CONSTRAINT_UNIQUE as exit 3;
consider mapping to a descriptive QuorumError::Usage with exit 2).
```

### F5 — Doc vs code: `task-update --status done` claims review spawning that doesn't happen (Priority 5)

**File:** `quorum/src/cli.rs:81` (docstring) vs `quorum-core/src/tasks.rs:570-682` (implementation)

The CLI docstring for `TaskUpdate` states:

> `done` — assignee-only, from `claimed`. Auto-spawns a review task.

But `task-update --status done` routes through `tasks::update()` (main.rs:360-367), not
through the lifecycle state machine. The `update()` function at tasks.rs:664-672
deactivates the lease and emits a `task_done` event, but does NOT spawn a review task
(that only happens via `apply_event` → lifecycle → effects). The `done` status is
intentionally NOT in the `restricted` list (tasks.rs:581), allowing it through the raw
update path.

This is likely by design — the passive (non-daemon) flow doesn't have a review pipeline.
But the CLI docstring is misleading: an agent reading the help text may expect review
spawning from `task-update --status done` and be surprised when it doesn't happen.

**Failure scenario:** An agent in a non-daemon setup uses `quorum task-update --status done`
expecting a review task to spawn. No review occurs; the task goes directly to `done`
terminal state. The agent's work is never reviewed. (Note: in the daemon flow, agents use
`quorum done` which goes through the mailbox → lifecycle path correctly.)

**Proposed fix-task:**

```
Either (a) add 'done' to the restricted list in tasks.rs:581 so
`task-update --status done` is rejected with a message directing
the caller to `quorum done`, or (b) update the CLI docstring to
clarify that review spawning only occurs through `quorum done`
(the daemon path), not through `task-update --status done`.
Option (b) is lower risk.
```

### F6 — Branch allocation retry exhaustion returns raw DB error (Priority 6)

**File:** `quorum-core/src/branches.rs:132-139`

When the 3-retry collision budget is exhausted (4 collisions: base + suffixes 1-3), the
4th SQLITE_CONSTRAINT_UNIQUE error falls through to `Err(e) => return Err(e.into())`
(line 138), which maps to `QuorumError::Db` → exit 3. This is classified as an
internal/DB error rather than the more accurate usage/input error (exit 2) — the agent
passed valid inputs, but branch namespace is exhausted for that slug.

**Failure scenario:** Pathological case: 4+ tasks with identical slugified titles + agent
names. The 4th allocation returns exit 3 with a raw SQLite constraint message rather
than exit 2 with an actionable error like "branch name collision exhausted retries;
use --branch-hint to specify a unique name."

**Proposed fix-task:**

```
After the retry loop exhausts in allocate_for_task, return a
QuorumError::Usage describing the branch-name collision rather
than propagating the raw SQLITE_CONSTRAINT_UNIQUE. E.g.:
Err(QuorumError::Usage(format!(
    "branch name collision exhausted after {attempt} retries \
     for '{base_branch}'; pass a unique --branch-hint"
)))
```
