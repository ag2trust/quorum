## Findings

### FINDING-1 (Priority 2 — silent stall / false alarm): `compute_health` and `stalled_count` are not state-aware

**File:** `quorum-core/src/stats.rs:1039-1061` (compute_health), `quorum-core/src/stats.rs:346-353` (stalled_count)

**Evidence:** Both `compute_health` and `stalled_count` filter daemon agents by `role == "worker"` and check `last_activity_age_secs` against a 180s threshold. Neither checks the worker's `phase` field.

```rust
// stats.rs:1040-1046
let has_dead = daemon_agents
    .iter()
    .filter(|d| d.role == "worker")
    .any(|d| match d.last_activity_age_secs {
        Some(age) => age > 180,
        None => true,
    });
```

When a worker completes its turn and enters `"awaiting-review"` phase (set at `serve/mod.rs:2607`), it stops producing stream events. Its `_daemon_live.json` sidecar stops updating. After 180s, `compute_health` marks the system `Stalled` and `stalled_count` increments — even though the worker is correctly idle and the reviewer is the expected actor.

**Failure scenario:** Daemon has 1 worker + 1 reviewer. Worker finishes in 60s, reviewer takes 300s. After 180s of reviewer work, the dashboard shows `HealthVerdict::Stalled` and `stalled_count=1`. An operator (or automated alert) sees a false stall alarm and may intervene unnecessarily. If the operator cancels the "stalled" task, the reviewer's work is wasted.

**Proposed fix-task:**
```
Filter `compute_health` and `stalled_count` to skip workers whose
`phase == "awaiting-review"`. Only workers in `"working"` phase are
expected to produce activity; `"awaiting-review"` workers are correctly
idle. Add a unit test: create a DaemonAgentView with role="worker",
phase="awaiting-review", last_activity_age_secs=300 — assert
compute_health returns OnTrack and stalled_count is 0.
```

### FINDING-2 (Priority 2 — silent stall): `Effect::NotifyOwner` is declared but never executed

**File:** `quorum-core/src/tasks.rs:503-523` (apply_event effect loop), `quorum-core/src/lifecycle.rs:96,182,228,244,271,293`

**Evidence:** The lifecycle transition table emits `Effect::NotifyOwner { reason }` in 5 transitions:
- `(Working, AgentFailed)` → lifecycle.rs:182
- `(InReview, AgentFailed)` → lifecycle.rs:244
- `(InReview, VerdictChanges)` at rework cap → lifecycle.rs:228
- `(Rework, AgentFailed)` → lifecycle.rs:271
- `(Merging, MergeFailed)` → lifecycle.rs:293

But `apply_event` (tasks.rs:503-523) handles only `SetAuthor`, `SetReviewer`, `IncrementReworkRound`, and `ReleaseLease` — everything else is `_ => {}`:

```rust
// tasks.rs:522
_ => {}
```

The serve loop's `fire_event` (mod.rs:3393-3432) logs the effect names but does not
dispatch `NotifyOwner` to any notification channel (no message posted, no alert sent).

**Failure scenario:** A task hits the rework cap (3 failed review rounds). The lifecycle emits `NotifyOwner { reason: "rework cap (3) exceeded" }` and transitions the task to `Failed`. The effect is silently dropped. The task creator is never informed that their task failed after consuming 3 agent sessions. The task sits in `Failed` indefinitely with no notification — the only way to discover it is to poll `quorum status` or `task-get`.

The design spec (docs/2026-06-23-quorum-design.md:429) defines `NotifyOwner { reason }` as "Alert the task creator." This is currently a no-op, violating the spec.

**Proposed fix-task:**
```
Implement NotifyOwner by posting a `kind:alert` message to the feed
(visible in `quorum status` and deliverable via `sync`). In apply_event,
add a match arm for Effect::NotifyOwner that calls
feed::post(conn, "system", "alert", ..., &reason, ...) inside the
existing transaction. Add tests: (1) AgentFailed in Working produces a
feed message with the failure reason; (2) rework cap exceeded produces
an alert.
```

### FINDING-3 (Priority 4 — test gap): No stall-injection tests

**File:** `quorum-core/src/stats.rs` (compute_health, stalled_count tests), `quorum/tests/cli_serve_watchdog.rs`

**Evidence:** The existing test `compute_health_new_thresholds` (stats.rs:2006-2041) tests threshold values against synthetic `DaemonAgentView` structs but:
- Does not test phase-awareness (all test views have default empty phase)
- Does not inject a stall scenario where one agent goes silent while another is working
- Does not verify escalation (banner + alert) within threshold

The task brief specifically requests: "stall-injection tests (agent goes silent in each state → banner + escalation within threshold)."

**Missing tests (named per convention):**

| Test name | What it verifies |
|-----------|-----------------|
| `test_awaiting_review_worker_not_stalled` | Worker with `phase="awaiting-review"` and `last_activity_age_secs=300` → `HealthVerdict::OnTrack`, `stalled_count=0` |
| `test_working_worker_stalled_after_180s` | Worker with `phase="working"` and `last_activity_age_secs=200` → `HealthVerdict::Stalled`, `stalled_count=1` |
| `test_reviewer_not_counted_in_stall` | Only-reviewer daemon with `last_activity_age_secs=300` → stalled_count=0 (stall only counts workers) |
| `test_mixed_fleet_stall_isolation` | One worker stalled, one awaiting-review → `stalled_count=1` (not 2) |

**Proposed fix-task:**
```
Add unit tests for compute_health and stalled_count with explicit phase
values on the DaemonAgentView inputs. Cover the 4 scenarios listed above.
These tests will initially fail (exposing FINDING-1) and pass after the
phase-awareness fix.
```

But NO tests exist for:

- `max_task_wall_secs` ceiling fire → worker killed → task released

The `check_wall_clock_limits` function (mod.rs:2556-2569) and the wall-clock watchdog
path (mod.rs:1966,2002) are untested at the integration level.

**Proposed fix-task:**
```
Add two integration tests to cli_serve_watchdog.rs:

   --max-task-wall-secs.
Note: fake-agent may need a mode that delays its result event to exercise
```

### FINDING-5 (Priority 4 — test gap): No ceiling-fire test for reviewer agents

**File:** `quorum/tests/cli_serve_watchdog.rs`, `quorum/src/serve/mod.rs:1960-1993`

**Evidence:** All watchdog integration tests cover worker ceiling kills only. The reviewer
ceiling enforcement path (mod.rs:1960-1993) follows the same pattern but is never
integration-tested. A reviewer exceeding a cost ceiling fires `AgentFailed` and calls
`teardown_reviewer` — if this path has a bug, it would leave the task stuck in `in-review`
with no reviewer and no respawn.

**Proposed fix-task:**
```
Add an integration test to cli_serve_watchdog.rs:
`reviewer_cost_limit_kills_reviewer` — seed a task, drive worker to done
with a PR, spawn reviewer with a low --max-task-tokens, verify the
reviewer is killed (WATCHDOG log) and the lifecycle fires AgentFailed
(which should respawn a new reviewer via SpawnReviewer effect).
```

## Out-of-scope handoffs

- **Tick loop audit (audit 2):** `executor.merge()` (mod.rs:1426) has no independent timeout. A hung `gh pr merge` blocks the tick loop indefinitely, stalling all agents. The `wait_for_checks` timeout (900s) bounds the checks wait, but the merge call itself is unbounded.
- **Recovery audit (audit 3):** `PendingReview` recovery on daemon restart (mod.rs:438-463) — verify the resurrected pending review correctly provisions a reviewer without re-executing the worker.
